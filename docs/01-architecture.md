## 컴포넌트별 역할

### k6 — 부하 생성기
가상 사용자(VU)를 N명 만들어 동시에 요청을 보낸다. **closed-loop** 방식이라
각 VU는 이전 요청의 응답을 받아야 다음 요청을 보낸다. 이 성질 때문에
Little's Law(`지연 = VU수 ÷ 처리량`)가 그대로 성립하고, 측정값을 이론값과
대조할 수 있다.

### Go 서버 — 측정 대상
의도적으로 병목을 심어둔 서버. 두 엔드포인트의 대비가 설계의 핵심이다.

| | `/api/users` | `/api/health` |
|---|---|---|
| 커넥션 풀 | 사용함 | 사용 안 함 |
| 부하 시 지연 | 급증 | 변화 없음 |
| 역할 | 관측 대상 | **대조군** |

대조군이 있어야 `"서버 전체가 느리다"`와 `"풀이 병목이다"`를 구분할 수 있다.
실제 장애 대응에서도 이 구분이 원인 좁히기의 첫 단계다.

### 커넥션 풀 — 병목
실제 DB 대신 **버퍼 채널 하나로 세마포어**를 만들어 썼다.
(→ 선택 이유는 [ADR-0001](adr/0001-simulated-connection-pool.md))

```go
type pool struct {
    slots chan struct{}  // 버퍼 크기 = 풀 크기
}
```

- `acquire()` — 빈 자리가 날 때까지 대기. `ctx` 타임아웃 시 포기하고 503
- `release()` — 자리 반납

대기 시간을 히스토그램으로 기록하기 때문에, **지연 중 얼마가 순수 대기인지**를
분리해서 볼 수 있다. 이게 "병목이 풀"이라고 단정할 수 있는 근거가 된다.

### 쿼리 비용 모델 — p99이 존재하는 이유
모든 요청이 똑같이 비싸면 p99이라는 개념 자체가 의미를 잃는다.
그래서 요청마다 비용을 다르게 만들었다.

```
95% → 10ms   (대부분의 사용자, 레코드 몇 개)
 5% → 400ms  (무거운 소수, 수만 건 조회)
```

풀이 5개뿐인데 비싼 요청이 자리를 오래 점유하면, 뒤에 줄 선 싼 요청까지
같이 막힌다. 이를 **head-of-line blocking**이라고 한다.
(→ 이 모델로 바꾼 경위는 [ADR-0002](adr/0002-heterogeneous-query-cost.md))

### Prometheus — 수집과 저장
**pull 방식**이다. 서버가 보내는 게 아니라 Prometheus가 5초마다
`/metrics`를 긁어간다(scrape). 서버는 현재 값을 노출만 하면 되고,
전송·재시도·버퍼링을 신경 쓸 필요가 없다.

알럿 규칙도 여기서 평가된다. 규칙이 참인 상태로 `for:` 시간만큼 유지되면
발화한다. 이 발화가 **2단계에서 트리아지 백엔드를 깨우는 트리거**가 된다.

### Grafana — 시각화
Prometheus에 쌓인 숫자를 그래프로 그린다. 데이터소스와 대시보드는
`grafana/provisioning/`으로 **자동 등록**되므로 UI에서 손으로 설정할 일이 없다.
대시보드 정의가 Git에 들어가므로 재현 가능하다.

## 실행 배치

Prometheus와 Grafana만 컨테이너로 띄우고 **Go 서버는 호스트에서 직접 실행**한다.

- 코드를 고치고 재시작하는 루프가 훨씬 빠르다
- 대신 컨테이너에서 호스트를 가리켜야 하므로 스크레이프 대상이 다르다

| 실행 방식 | 설정 파일 | 스크레이프 대상 |
|---|---|---|
| 네이티브 | `prometheus/prometheus.yml` | `localhost:8080` |
| 도커 | `prometheus/prometheus.docker.yml` | `host.docker.internal:8080` |
