# 05. 로드맵

## 전체 설계

최종 목표는 **트래픽 이상을 감지하면 백엔드가 AI를 호출해 원인을 판단하는 시스템**이다.

```
[트래픽]
   ↓
[Go 서버] ──메트릭──> [Prometheus]
                          ↓
                 [알럿 규칙]            ← 1단계: 규칙 (싸고 결정론적)
                          ↓ webhook
   ┌──────────────────────────────────────┐
   │        트리아지 백엔드                 │
   │                                      │
   │  ① 정규화      공통 스키마로 변환      │
   │  ② 중복제거·상관  fingerprint 묶기     │  ← 2단계: 알럿 폭풍 방어
   │  ③ 레이트리밋·서킷브레이커             │
   │  ④ GATHER     컨텍스트 수집           │  ← AI 없이 수행
   │  ⑤ REASON     AI 1회 호출             │  ← 여기서만 AI
   │  ⑥ 출력       Slack / 이슈 / 대시보드  │
   └──────────────────────────────────────┘
```

설계 원칙은 하나다:

> **AI는 탐지기가 아니라 설명기다.**

탐지는 싸고 결정론적인 것(임계값, 이상탐지)이 한다.
AI는 "이상하다"가 확정된 뒤에 **왜 그런지**를 설명하러 들어온다.
(→ [ADR-0003](adr/0003-ai-as-explainer-not-detector.md))

---

## 1단계 — 병목 재현과 측정 ✅

**목표:** p99이 무너지는 걸 눈으로 보고, 왜 그런지 설명할 수 있게 된다.

- [x] RED 메트릭을 노출하는 Go 서버
- [x] 의도적 병목 (작은 커넥션 풀)
- [x] Prometheus + Grafana 자동 프로비저닝
- [x] k6 계단식 부하 스크립트
- [x] 알럿 규칙 3종
- [x] 부하 구간별 실측 → [실험 기록](03-experiments.md)
- [x] 이질적 비용 모델로 p99 발산 재현
- [x] 풀 크기 튜닝 실험 + 성능 게이트 양방향 확인
- [x] 스택 통합 검증 (스크레이프 / 대시보드 / 알럿 발화)
- [x] open-loop 부하 모델 도입 + closed-loop과 비교 측정

**여기서 나온 것:** p99/p50 격차가 최대 42배까지 벌어지는 구간을 찾았고,
처리량 천장(169 RPS)이 이론값과 2% 이내로 일치함을 확인했다.
풀을 10배로 키워도 p99이 절반밖에 안 줄어드는 것을 통해
**큐 대기와 이질성은 다른 문제**임을 확인했다.
알럿은 설계 의도대로 **원인(`DBPoolSaturated`)이 결과(p99, 503)보다 먼저** 울었다.

## 2단계 — 트리아지 백엔드 골격 (AI 없음)

**목표:** 알럿을 받아 **AI에게 넘길 준비가 된 컨텍스트 묶음**을 만든다.

- [ ] Alertmanager 추가 + webhook 수신 엔드포인트
- [ ] 알럿 정규화 (공통 스키마)
- [ ] fingerprint 기반 중복 제거
- [ ] 디바운스 (같은 fingerprint는 N분 내 1회)
- [ ] 레이트리밋 + 서킷브레이커
- [ ] **GATHER 단계** — 컨텍스트 수집기
  - [ ] 알럿 전후 10분 메트릭 윈도우 (PromQL)
  - [ ] 관련 로그 N줄
  - [ ] 최근 설정 변경 이력
  - [ ] 유사 과거 인시던트
- [ ] 수집 결과를 JSON으로 덤프 (AI 없이 사람이 읽어봄)

**의도적으로 AI를 안 붙인다.** 수집된 컨텍스트만 보고 사람이 원인을
짚을 수 없다면, AI도 못 짚는다. **먼저 컨텍스트 품질을 확보한다.**

핵심 방어 장치는 **디바운스와 서킷브레이커**다. 장애 시 알럿 1000개가
한꺼번에 울리면 AI를 1000번 호출하게 된다. 이걸 막는 유일한 방법이고,
안 넣으면 반드시 당한다.

---

## 3단계 — AI 연결

**목표:** 수집된 컨텍스트로 구조화된 진단을 받는다.

- [ ] REASON 단계 — AI 1회 호출
- [ ] 구조화된 출력 스키마 강제
      ```json
      {
        "severity": "warning|critical",
        "likely_cause": "...",
        "evidence": ["...", "..."],
        "confidence": 0.0,
        "suggested_action": "..."
      }
      ```
- [ ] 토큰 예산 상한
- [ ] 권한 경계 — **read-only로 시작.** 롤백·스케일 같은 액션 없음
- [ ] 출력 전달 (Slack 또는 로컬 대시보드)

산문으로 받으면 후속 자동화가 불가능하므로 **스키마를 강제**한다.
GATHER와 REASON을 분리했기 때문에 토큰 예산이 통제된다 —
AI에게 빈 프롬프트를 주고 "알아서 조사해"가 아니라,
**정리된 사실 묶음**을 건네고 판단만 시킨다.

---

## 4단계 — 정확도 측정

**목표:** 이 시스템을 믿어도 되는지 숫자로 안다.

- [ ] 재현 가능한 장애 시나리오 4종 (→ [실험 4](03-experiments.md))
- [ ] 각 시나리오의 기대 진단 고정 (골든셋)
- [ ] 트리아지 정확도 측정 스크립트
- [ ] 프롬프트·컨텍스트 개선 후 회귀 확인

**이 단계가 있고 없고가 "돌아는 간다"와 "믿을 만하다"의 차이다.**

여기서 부하 테스트가 두 번째 역할을 한다. **정답을 아는 장애를
내가 만들 수 있으므로**, AI 진단의 정확도를 채점할 수 있다.
k6가 트리아지 시스템의 테스트 하네스가 되는 셈이다.

특히 **"장애가 아니라 단순 용량 부족"**을 구분하는지 봐야 한다.
이걸 못 하면 트리아지는 쓸모가 없다.
