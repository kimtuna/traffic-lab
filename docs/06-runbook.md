## 0. 터미널 배치

터미널 3개를 열어두면 편하다.

| | 역할 | 명령 |
|---|---|---|
| **A** | 서버 | `go run .` |
| **B** | 부하 | `k6 run k6/load.js` |
| **C** | 확인 | `curl` / `docker compose` |

브라우저는 두 탭:
- **대시보드** → http://localhost:3000/d/traffic-lab
- **알럿** → http://localhost:9090/alerts

## 1. 기동

```bash
cd ~/Desktop/traffic-lab
docker compose up -d     # Prometheus + Grafana
go run .                 # 터미널 A
```

서버가 뜨면 이 세 줄이 나온다. **마지막 줄의 숫자를 기억해두자** —
부하가 이 선을 넘으면 큐가 쌓이기 시작한다.

```
pool=5  acquire_timeout=3s
쿼리 비용: 10ms (95%) / 400ms (5%)  평균 29.5ms
이론상 한계 처리량 ≈ 169 RPS (풀 5개 / 평균 29.5ms)
```

### 기동 확인 (터미널 C)

```bash
curl -s -o /dev/null -w "서버 %{http_code}\n" http://localhost:8080/api/health
curl -s http://localhost:9090/api/v1/targets | grep -o '"health":"[a-z]*"'
```

`서버 200` 과 `"health":"up"` 이 나오면 준비 완료.
`up`이 아니면 [7. 문제 해결](#7-문제-해결)로.

## 2. 테스트 시나리오

### 시나리오 0 — 연결 확인 (30초)

```bash
k6 run k6/smoke.js
```

3 VU로 가볍게 때린다. 에러가 없고 대시보드에 선이 그려지면 배선이 정상이다.
**기대값:** p50 ≈ 11ms, 에러 0건, RPS ≈ 70

### 시나리오 1 — 기본 계단식 부하 (3분) ★

```bash
k6 run k6/load.js
```

5 → 20 → 50 → 100 VU로 올라갔다 내려온다. **이 프로젝트의 본 실험이다.**
대시보드를 띄워놓고 아래 [3. 무엇을 볼 것인가](#3-무엇을-볼-것인가)를 따라간다.

**기대 결과:** p95 690ms로 **게이트 실패** (종료 코드 99). 이건 의도된 것이다.

### 시나리오 2 — 풀을 키우면 달라지는가

터미널 A에서 서버를 끄고(`Ctrl+C`) 다시:

```bash
POOL_SIZE=50 go run .
```

같은 부하를 다시 건다. 비교표:

| | `POOL_SIZE=5` | `POOL_SIZE=50` |
|---|---:|---:|
| 이론 한계 | 169 RPS | 1695 RPS |
| p95 | 690.47ms | 284.59ms |
| p99 | 863.91ms | **482.23ms** |
| 게이트 | ❌ 99 | ✅ 0 |

**질문:** 풀을 10배 키웠는데 왜 p99은 절반밖에 안 줄었나?

<details>
<summary>답</summary>

482ms는 큐 대기가 아니라 **비싼 쿼리 자체의 비용**이다(400ms × 지터).
풀 크기는 큐 대기를 줄일 뿐, 요청 간 비용 차이는 못 없앤다.
p99을 더 낮추려면 풀이 아니라 그 400ms짜리 쿼리를 손봐야 한다.
</details>

### 시나리오 3 — 병목을 극단으로

```bash
POOL_SIZE=1 go run .
```

한계가 34 RPS로 떨어진다. 5 VU만 걸어도 무너진다.

```bash
k6 run --vus 5 --duration 30s k6/smoke.js
```

### 시나리오 4 — 503을 직접 만들어보기

기본 설정에서는 100 VU로도 503이 안 난다(3초 안에 커넥션을 얻으므로).
둘 중 하나로 만들 수 있다.

```bash
# 방법 1 — 부하를 극단으로
k6 run --vus 500 --duration 20s k6/smoke.js
# → 에러율 약 7.3%

# 방법 2 — 타임아웃을 줄여서 (서버 재시작 필요)
ACQUIRE_TIMEOUT_MS=200 go run .
k6 run --vus 100 --duration 30s k6/smoke.js
```

확인:
```bash
curl -s http://localhost:8080/metrics | grep -E 'timeouts_total|503'
```
`db_pool_timeouts_total`과 503 응답 수가 **정확히 일치**해야 한다.

### 시나리오 5 — 쿼리 자체가 느려지면

```bash
QUERY_MS=50 SLOW_QUERY_MS=800 go run .
```

풀 크기는 그대로인데 한계 처리량이 떨어진다.
**"풀이 작아서"와 "쿼리가 느려서"는 다른 문제**이고, 대시보드에서
구분할 수 있어야 한다 → 6번 패널(대기 시간)이 판단 근거다.

## 3. 무엇을 볼 것인가

### 시나리오 1을 돌리면서 이 순서로

**① 0~30초 (5 VU) — 여유**

3번 패널을 본다. p50이 바닥에 붙어 있다(~11ms).
그런데 **p99은 이미 460ms 근처에 떠 있다.**

> 이 시점에 평균만 봤다면 "완벽하게 건강함"이라고 판단했을 것이다.
> 실제로는 100명 중 1명이 0.5초를 기다리고 있다.

**② 30~90초 (20~50 VU) — 포화 시작** ★ 핵심 구간

5번 패널로 옮긴다.

```
사용 중(db_pool_in_use)        5에서 평평해진다  ← 풀이 꽉 참
처리 중 요청(inflight)          계속 올라간다
──────────────────────────────────────────
그 차이 = 큐에서 대기 중인 요청 수
```

동시에 3번 패널에서 **p50이 올라오기 시작**한다(11ms → 35 → 84ms).
p99과의 격차가 42배에서 7배로 좁혀진다.

**③ 90~150초 (100 VU) — 전면 포화**

1번 패널을 본다. **RPS가 165에서 더 안 오른다.**
VU를 100까지 올렸는데도 처리량은 그대로다.

> 포화 이후 늘어나는 건 처리량이 아니라 큐 길이뿐이고, 큐 길이가 곧 지연이다.

6번 패널에서 대기 p99이 0.96초까지 올라간다.
**이게 전체 p99(0.98초)의 98%다.** → 병목은 풀이다.

**④ 150~180초 (0 VU) — 회복**

모든 선이 떨어진다. 회복이 얼마나 빨리 되는지도 정보다.

**⑤ 대조군 확인**

1번 패널에서 `/api/health`와 `/api/users`의 RPS는 같지만,
3번 패널의 지연은 `/api/users`만 치솟는다.
→ **"서버가 느리다"가 아니라 "풀이 병목이다"**

## 4. 판정표

부하 중 아무 때나 대시보드를 보고 현재 상태를 판정할 수 있다.

| 신호 | 🟢 정상 | 🟡 경고 | 🔴 붕괴 |
|---|---|---|---|
| **p50** | ~11ms | 35~85ms | >500ms |
| **p99** | ~460ms | 500~900ms | >1s |
| **p99/p50** | 40배 | 5~15배 | <2배 |
| **RPS** | 부하 따라 증가 | 165에서 고정 | 165 고정 |
| **풀 사용 중** | <5 | 5에서 평평 | 5에서 평평 |
| **큐 길이** | 0 | 10~75 | >100 |
| **에러율** | 0% | 0% | >0% |

### 이 표에서 헷갈리기 쉬운 두 가지

**p99/p50 격차가 클수록 나쁜 게 아니다.** 오히려 반대다.

```
40배 → 이질성이 막 드러나기 시작. 지금이 개입할 때
 2배 → 이미 모두가 느림. 늦었다
```

격차가 **좁혀졌다는 건 회복이 아니라 전면 포화**라는 뜻이다.

**에러율 0%가 건강하다는 뜻이 아니다.** 100 VU 구간에서 p99이 1초인데
에러는 0건이다. 사용자는 1초씩 기다리고 있지만 실패는 아니다.
→ **에러율 알럿만 걸어두면 너무 늦게 안다.**

## 5. 알럿 확인

http://localhost:9090/alerts

부하 중 이 순서로 색이 바뀐다.

| 순서 | 알럿 | 조건 | 의미 |
|---|---|---|---|
| 1️⃣ | `DBPoolSaturated` | 대기 p99 > 100ms | **원인** |
| 2️⃣ | `HighP99Latency` | p99 > 1s | 결과 |
| 3️⃣ | `HighErrorRate` | 5xx > 1% | 최종 결과 |

`for: 30s`가 걸려 있어서 조건이 30초 지속돼야 빨간색(FIRING)이 된다.
그 전에는 노란색(PENDING)이다.

**원인 알럿이 결과 알럿보다 먼저 울어야 한다.** 이 시간차가
3단계에서 AI 트리아지가 개입할 여유가 된다.

## 7. 문제 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| `localhost:3000` 응답 없음 | 컨테이너가 내려감 | `docker compose up -d` |
| Docker 데몬 응답 없음 | Docker Desktop이 약관 화면에서 대기 | Docker Desktop 창에서 동의 |
| 스크레이프 `health=down` | Go 서버가 안 떠 있음 | 터미널 A에서 `go run .` |
| 그래프가 비어 있음 | 부하를 안 걸었거나 시간 범위가 어긋남 | 우측 상단 `Last 15 minutes` 확인 |
| 대시보드가 안 보임 | 프로비저닝 실패 | `docker compose logs grafana` |
| 재시작하니 과거 그래프가 사라짐 | **정상.** 볼륨을 안 붙임 | 보존이 필요하면 볼륨 추가 |
| k6가 실패로 끝남 | **정상.** 기본 설정은 게이트 실패가 의도 | [시나리오 2](#시나리오-2--풀을-키우면-달라지는가) 참고 |

### 종료

```bash
docker compose down      # 컨테이너 정리
# 터미널 A에서 Ctrl+C    # 서버 종료
```
