# 07. 실무 규모 부하 테스트

장난감 실험실과 실무 사이의 격차, 그리고 그것을 메우는 방법.

---

## 격차 1 — 부하 모델 (가장 중요)

`k6/load.js`는 **closed-loop**이다. "동시 사용자 100명"을 만든다.
각 VU는 응답을 받아야 다음 요청을 보낸다.

여기에 함정이 있다. **서버가 느려지면 요청도 같이 느려진다.**
서버가 스스로를 보호하는 셈이다. 실제 사용자는 그렇지 않다.
내 서버가 느리다고 사용자가 접속을 덜 하지는 않는다.

실제 트래픽은 **open-loop**이다. 요청은 서버 상태와 무관하게 도착한다.

> closed-loop 테스트로 지연을 측정하면 **실제보다 좋게 나온다.**
> 이 현상을 **coordinated omission**이라 한다.

### 직접 측정한 차이

같은 서버(풀 5개, 한계 169 RPS)에 60초씩 두 방식으로 부하를 걸었다.

| | closed-loop<br>(동시 100명) | open-loop<br>(초당 200건 도착) |
|---|---:|---:|
| p50 | 589.32ms | **2.73s** |
| p95 | 964.96ms | 3.00s |
| p99 | 1.16s | **3.32s** |
| **에러율** | **0.00%** | **7.48%** (868건) |
| 처리량 | 162.98 RPS | 183.39 RPS |
| 미발사 요청 | 0 | 408 |

**closed-loop 결과만 보면 "에러 0건, p99 1.16초 — 배포해도 되겠다"가 된다.**
같은 서버가 open-loop에서는 요청 13건 중 1건을 실패시키고 있었다.

원인은 단순하다. 서버 용량은 169 RPS인데 200 RPS가 들어온다.
초당 31건씩 큐가 쌓이고, 3초(`ACQUIRE_TIMEOUT_MS`)를 넘긴 요청이 503이 된다.
closed-loop에서는 이 상황이 애초에 만들어지지 않는다 —
100명이 기다리는 동안 새 요청이 안 들어오기 때문이다.

### 그래서 어떻게 하나

k6의 **arrival-rate executor**를 쓴다. VU는 더 이상 부하의 단위가 아니라
"도착률을 채우기 위한 일꾼"이 된다.

```javascript
scenarios: {
  steady: {
    executor: 'ramping-arrival-rate',   // 또는 constant-arrival-rate
    startRate: 20, timeUnit: '1s',
    preAllocatedVUs: 100,
    maxVUs: 2000,                        // 넉넉히
    stages: [{ duration: '2m', target: 200 }],
  },
},
```

→ [`k6/scenarios/open-loop.js`](../k6/scenarios/open-loop.js)

### ⚠️ `dropped_iterations`를 반드시 확인할 것

위 측정에서 **408건이 아예 발사되지 못했다.** VU가 모자라서
k6가 요청을 보내려다 포기한 것이다.

```javascript
thresholds: {
  'dropped_iterations': ['count<1'],
}
```

**이 값이 0이 아니면 측정 자체가 무효다.** 의도한 부하를 걸지 못했으므로
결과는 실제보다 낙관적으로 나온다. `maxVUs`를 올려서 다시 측정해야 한다.

## 격차 2 — 목표 숫자가 없다

"부하를 얼마나 걸어야 하나"에 답하지 못하면 테스트는 의미가 없다.
비즈니스 숫자에서 역산한다.

```
① 일일 요청 수   = DAU × 1인당 요청 수
② 평균 RPS      = ① ÷ 86,400
③ 피크 RPS      = ② × 피크 배수
④ 설계 목표      = ③ × 헤드룸(2배)
```

### 피크 배수

| 서비스 성격 | 피크/평균 |
|---|---|
| 일반 웹·앱 (낮 시간 집중) | 3~5배 |
| 국내 서비스 (점심·저녁 쌍봉) | 4~6배 |
| 커머스 정기 세일 | 10~30배 |
| 티켓팅·수강신청 | **100배 이상** |

### 예시

DAU 100만, 1인당 하루 50요청인 서비스:

```
① 5,000만 요청/일
② 579 RPS (평균)
③ 2,316 RPS (피크 배수 4배)
④ 4,632 RPS (헤드룸 2배)
```

**breakpoint 테스트로 실제 한계를 찾아 ④와 비교한다.**
한계가 ④보다 낮으면 증설하거나 병목을 고쳐야 한다.

→ [`k6/scenarios/breakpoint.js`](../k6/scenarios/breakpoint.js)

실제로 돌려보면 `abortOnFail`이 SLO를 깨는 순간 테스트를 중단한다.
이 실험실에서 `MAX_RATE=300`으로 실행하니 **78초 지점에서 중단**됐다.
stage 구성상 그 시점의 도착률은 약 170 RPS로, **이론 한계 169 RPS와 일치**한다.

> breakpoint 테스트의 결과물은 "통과/실패"가 아니라 **숫자 하나**다.
> 그 숫자가 용량 계획의 기준선이 된다.

관측 데이터가 있다면 추정보다 그쪽이 낫다:
```promql
max_over_time(sum(rate(http_requests_total[1m]))[30d:1m])
```

## 격차 3 — 테스트 종류를 구분하지 않는다

"부하 테스트"는 하나가 아니다. 목적이 다른 6가지가 있다.

| 종류 | 부하 | 시간 | 답하는 질문 | 스크립트 |
|---|---|---|---|---|
| **smoke** | 최소 | 1분 | 배선이 맞나 | `k6/smoke.js` |
| **load** | 예상 피크 | 10~30분 | 평소 트래픽을 견디나 | `scenarios/open-loop.js` |
| **stress** | 피크 초과 | 10~30분 | 한계 넘으면 어떻게 죽나 | `RATE=400 open-loop.js` |
| **breakpoint** | 계속 증가 | ~30분 | 정확히 어디서 무너지나 | `scenarios/breakpoint.js` |
| **spike** | 급격한 폭증 | 5분 | 갑작스런 폭증을 견디나 | `scenarios/spike.js` |
| **soak** | 평상시 | **4~24시간** | 오래 돌리면 새는가 | `scenarios/soak.js` |

### 우선순위

처음이라면 **smoke → breakpoint → load → spike → soak** 순.

breakpoint를 먼저 하는 이유는 **한계를 모르면 load 테스트의 목표를
정할 수 없기 때문**이다. 한계를 찾고, 그 70% 수준에서 load 테스트를 돌린다.

### soak에서만 보이는 것

짧은 테스트로는 절대 안 잡힌다.
- 메모리 누수 (힙 우상향)
- 커넥션 / 파일 디스크립터 누수
- 로그·디스크 누적
- 캐시 무한 증가

**부하 크기가 아니라 시간에 따른 기울기**를 본다.
시작과 끝의 p99이 같아야 한다.

### spike에서 봐야 할 것

최고점의 지연이 아니라 **회복 시간**이다.
폭증이 끝났는데도 큐가 남아 한참 느린 경우가 많다.
`spike.js`의 마지막 60초가 그 관찰 구간이다.

## 격차 4 — 부하 생성기가 병목이 된다

지금은 k6와 서버가 **같은 노트북**에서 돌고 있다. CPU를 서로 뺏는다.
수천 RPS 이상에서는 측정값을 믿을 수 없다.

### 신호

| 증상 | 의미 |
|---|---|
| `dropped_iterations > 0` | VU 부족. 부하를 못 걸었다 |
| 서버 CPU는 여유로운데 RPS가 안 오름 | 생성기가 한계 |
| k6 프로세스 CPU 100% | 생성기가 한계 |

### 해결

1. **생성기와 서버를 분리** — 최소한 다른 머신
2. **분산 부하** — k6를 여러 노드에서 실행, 또는 k8s operator
3. **관리형** — Grafana Cloud k6 등

참고로 단일 노드 k6는 보통 **수만 RPS**까지는 낸다.
그보다 먼저 네트워크나 로컬 포트 고갈(`ephemeral port`)이 걸리는 경우가 많다.

## 격차 5 — 환경이 다르면 결과도 다르다

**이게 실무에서 가장 자주 틀리는 부분이다.**

| 항목 | 왜 중요한가 |
|---|---|
| **데이터 볼륨** | 레코드 100건과 1000만 건은 완전히 다른 쿼리 플랜을 탄다. **가장 자주 간과된다** |
| 인스턴스 사양 | CPU/메모리가 다르면 GC 거동부터 달라진다 |
| 네트워크 | 같은 머신(0.1ms)과 실제 네트워크(1~50ms)는 다르다 |
| 캐시 상태 | 캐시가 비어 있으면 전부 DB로 간다 |
| 동시 배치 작업 | 실제 운영에는 크론·배치가 같이 돈다 |

### 데이터 볼륨이 특히 중요한 이유

인덱스가 없어도 레코드 100건이면 풀스캔이 1ms다. 테스트는 통과한다.
1000만 건에서는 같은 쿼리가 10초다.
**스테이징 데이터가 적으면 이 문제를 절대 못 잡는다.**

운영 데이터를 가져올 때는 반드시 **익명화**하고,
개인정보 처리 규정을 확인한다.

### 워밍업

측정 전 1~2분은 버린다.
- JIT 컴파일 (JVM 등)
- 커넥션 풀 초기 생성
- 캐시 채우기
- CPU 주파수 스케일링

k6에서는 워밍업 stage를 두고 그 구간을 분석에서 제외한다.

## 격차 6 — RED만으로는 원인을 못 짚는다

부하 테스트 중에는 **USE**도 같이 봐야 한다.

| | 관점 | 지표 |
|---|---|---|
| RED | 요청이 어떤가 | Rate / Errors / Duration |
| **USE** | 자원이 어떤가 | Utilization / Saturation / Errors |

실무에서 추가로 붙이는 것:

| 대상 | exporter | 봐야 할 것 |
|---|---|---|
| 호스트 | `node_exporter` | CPU, 메모리, 디스크 IO, 네트워크 |
| DB | `postgres_exporter` | 커넥션 수, lock wait, 느린 쿼리, 캐시 적중률 |
| 런타임 (Go) | 기본 제공 | `go_goroutines`, `go_gc_duration_seconds`, 힙 |
| 컨테이너 | `cAdvisor` | throttling, OOM kill |

Go는 `promhttp`를 쓰면 런타임 지표가 자동으로 붙는다.
**`go_goroutines`가 계속 우상향하면 고루틴 누수**이고, soak 테스트에서 잡힌다.

### 병목은 옮겨 다닌다

이 실험실의 병목은 커넥션 풀 하나로 고정돼 있다.
실제 시스템에서는 하나를 고치면 다음이 드러난다.

```
커넥션 풀  →  DB CPU  →  느린 쿼리(N+1)  →  락 경합
   →  외부 API  →  앱 CPU  →  GC  →  네트워크 대역
```

**부하 테스트는 한 번 하고 끝나는 게 아니라, 병목을 하나씩 벗겨내는 반복이다.**

## 격차 7 — 안전과 절차

### 운영 환경에 부하를 걸기 전에

- [ ] **승인을 받았는가** (권한 없는 부하 테스트는 사고이자 문제가 될 수 있다)
- [ ] 관계 팀에 일정을 공유했는가 (인프라, 보안, 온콜)
- [ ] 클라우드 제공자 정책을 확인했는가
- [ ] 외부 연동(결제, SMS, 푸시)을 **반드시 목(mock) 처리**했는가
- [ ] 알럿을 일시 억제했는가 (온콜이 새벽에 깨지 않도록)
- [ ] 중단 기준과 중단 방법을 정했는가
- [ ] 비용 상한을 확인했는가 (오토스케일이 폭주할 수 있다)

### 권장 순서

1. **로컬** — 지금 하고 있는 단계
2. **스테이징** — 운영과 같은 사양, 운영급 데이터 볼륨
3. **운영 (canary)** — 트래픽 일부만, 관측하며 점진적으로

운영에서 바로 전량 부하를 거는 건 하지 않는다.

### 기록

매 실행마다 남긴다. 안 남기면 비교가 불가능하다.
- 커밋 해시 / 이미지 태그
- 환경 설정 (`POOL_SIZE` 등 전부)
- 인프라 사양
- 데이터 볼륨
- k6 요약 전문

→ [실험 기록](03-experiments.md)이 그 예시다.

## 이 실험실에서 바로 해볼 것

```bash
# 1. 한계를 찾는다
k6 run k6/scenarios/breakpoint.js

# 2. 그 70% 수준에서 정상 부하 테스트
RATE=120 k6 run k6/scenarios/open-loop.js

# 3. 폭증을 견디는지
k6 run k6/scenarios/spike.js

# 4. closed vs open 차이를 직접 확인
k6 run k6/load.js                          # 에러 0%
RATE=200 k6 run k6/scenarios/open-loop.js  # 에러 7.5%
```

4번이 이 문서의 핵심이다. **같은 서버, 다른 결론.**
