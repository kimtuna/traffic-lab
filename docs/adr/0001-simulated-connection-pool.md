# ADR-0001. 실제 DB 대신 세마포어로 커넥션 풀을 모사한다

**상태:** 채택 · 2026-09-15

## 맥락

이 프로젝트의 목표는 **커넥션 풀 고갈로 p99이 무너지는 과정을 관측**하는 것이다.
그러려면 "요청이 제한된 자원을 기다리다 지연된다"는 상황이 필요하다.

가장 자연스러운 선택은 실제 PostgreSQL을 띄우고 `pgxpool`의 `MaxConns`를
작게 잡는 것이다. 하지만 목표 대비 비용을 따져볼 필요가 있었다.

## 결정

**버퍼 채널 하나로 세마포어를 만들어 커넥션 풀을 모사한다.**

```go
type pool struct {
    slots chan struct{}  // 버퍼 크기 = 풀 크기
}
```

`acquire()`는 채널에 값을 넣는 데 성공해야 통과하고,
빈 자리가 없으면 블록된다. `release()`는 값을 빼서 자리를 돌려준다.
쿼리 실행은 `time.Sleep()`으로 대체한다.

## 고려한 대안

### 대안 A — 실제 PostgreSQL + pgxpool
- 장점: 현실적. `pgxpool.Stat()`으로 진짜 풀 지표를 얻을 수 있고,
  실제 DB 튜닝 경험도 같이 쌓인다
- 단점: 컨테이너 1개 추가, 스키마와 시드 데이터 필요,
  DB 자체 성능 특성(버퍼 캐시, 체크포인트, autovacuum)이 변수로 섞여 들어옴

**기각 이유:** 마지막 항목이 결정적이었다. DB의 성능 변동이 섞이면
**"지연이 풀 대기 때문인지 DB 내부 사정 때문인지 분리할 수 없다."**
1단계의 목표는 큐잉 현상 자체를 깨끗하게 관측하는 것이므로,
변수를 줄이는 쪽이 맞다.

### 대안 B — `golang.org/x/sync/semaphore`
- 장점: 의도가 명시적으로 드러남, 가중치 있는 획득 지원
- 단점: 의존성 1개 추가. 버퍼 채널로 3줄이면 되는 일

**기각 이유:** 채널 세마포어는 Go의 관용적 표현이고,
읽는 사람이 배우는 바도 더 크다.

## 결과

**좋은 점**
- 의존성 없이 `go run .` 하나로 전체 실험이 돌아간다
- 풀 크기·쿼리 시간을 환경변수로 즉시 바꿔가며 실험할 수 있다
- **이론값과 측정값을 대조할 수 있다.** 서비스 시간이 정확히 알려져 있으므로
  `한계 처리량 = 풀 크기 ÷ 평균 서비스 시간`을 계산해 검증할 수 있고,
  실제로 169 RPS 예측이 측정값과 2% 이내로 맞았다
  (→ [실험 2](../03-experiments.md))

**나쁜 점**
- 실제 DB 튜닝 경험은 얻지 못한다
- `time.Sleep()`은 진짜 쿼리와 달리 CPU를 안 쓴다.
  CPU 포화가 얽히는 실제 상황은 재현되지 않는다
- 커넥션 생성 비용, 재연결, 트랜잭션 같은 실제 풀의 복잡성이 없다

**감수하는 이유:** 1단계는 "큐잉으로 p99이 무너진다"를 이해하는 단계다.
DB 고유 문제는 그 다음이다.

## 재검토 조건

다음 중 하나라도 해당하면 실제 DB로 교체한다.

- 쿼리 최적화나 인덱스 튜닝이 학습 목표에 포함될 때
- CPU 포화와 커넥션 대기가 **동시에** 일어나는 상황을 봐야 할 때
- AI 트리아지가 실제 DB 지표(lock wait, checkpoint 등)를 읽어야 할 때
