# 04. 용어 사전

이 프로젝트를 이해하는 데 필요한 용어만 모았다.

---

## 측정

### 퍼센타일 (p50 / p95 / p99)
응답 시간을 **정렬해서 몇 번째냐**로 보는 방식.

요청 100개 중 99개가 10ms, 1개가 5000ms라면:
- 평균 = 약 60ms — 훌륭해 보인다
- p50 = 10ms — 보통 사용자
- p99 = 5000ms — 가장 운 나쁜 1%

평균은 꼬리를 숨긴다. **사용자 100명 중 1명이 5초를 기다린 사실**이
평균 60ms 안에 묻힌다. 그래서 꼬리 분위수를 본다.

> p99 = 100번 중 1번. 사용자가 하루에 100번 요청하면 매일 한 번씩 겪는다.

### RED 메트릭
요청 처리 서비스에서 봐야 할 최소 3가지.

| | 뜻 | 이 프로젝트에서 |
|---|---|---|
| **R**ate | 처리량 | 초당 요청 수 (RPS) |
| **E**rrors | 실패율 | 5xx 비율 |
| **D**uration | 응답 시간 | p50 / p95 / p99 |

### Counter / Gauge / Histogram
Prometheus의 메트릭 타입.

| 타입 | 성질 | 예 |
|---|---|---|
| Counter | 증가만 함 | 누적 요청 수 |
| Gauge | 오르내림 | 현재 사용 중인 커넥션 |
| Histogram | 값의 분포 | 응답 시간 |

Counter는 raw 값이 의미 없어 항상 `rate()`를 씌운다.
분위수를 뽑으려면 반드시 Histogram이어야 한다.

### 버킷 (bucket) / `le`
Histogram이 분포를 저장하는 방식. "0.1초 이하가 몇 건"처럼
경계값별 누적 개수를 센다. `le`는 *less than or equal*.

## 부하

### VU (Virtual User, 가상 사용자)
k6가 만들어내는 가상의 동시 사용자. VU 100 = 100명이 동시에 요청.

### closed-loop / open-loop
- **closed-loop** — 각 VU가 응답을 받아야 다음 요청을 보냄 (k6 기본)
- **open-loop** — 응답과 무관하게 정해진 속도로 계속 요청

closed-loop에서는 동시 요청 수가 VU 수로 고정되므로 Little's Law가
그대로 성립한다. 반면 실제 사용자 트래픽은 open-loop에 가깝다.

### Little's Law
```
평균 동시 요청 수 = 처리량 × 평균 지연
```
closed-loop 부하에서는 동시 요청 수 = VU 수이므로:
```
지연 = VU 수 ÷ 처리량
```
[실험 1](03-experiments.md)에서 100 VU ÷ 98.6 RPS = 1.01s가
측정된 p50과 정확히 일치했다.

### threshold (임계값)
k6에서 테스트의 통과/실패를 가르는 기준.
```javascript
thresholds: {
  'http_req_duration': ['p(99)<1000'],
  'http_req_failed': ['rate<0.01'],
}
```
CI에 걸면 그대로 **성능 게이트**가 된다.

## 병목

### 커넥션 풀
DB 커넥션을 미리 N개 만들어두고 돌려 쓰는 구조.
커넥션 생성 비용이 비싸서 매번 만들 수 없기 때문이다.

풀이 꽉 차면 요청은 **빈 자리가 날 때까지 대기**한다.
이 대기가 지연의 주범이 되는 경우가 매우 흔하다.

### 풀 고갈 (pool exhaustion)
대기해도 커넥션을 못 얻어 요청이 실패하는 상태.
보통 타임아웃 후 503으로 나타난다.

### head-of-line blocking
앞에 선 느린 요청 때문에 뒤의 빠른 요청까지 막히는 현상.

이 프로젝트에서 p99이 튀는 직접적 원인이다. 400ms짜리 쿼리가
5개뿐인 커넥션을 점유하면, 10ms면 끝날 요청들이 그 뒤에서 기다린다.

### 포화 (saturation)
자원이 100% 사용 중이라 더 이상 처리량이 늘지 않는 상태.
[실험 2](03-experiments.md)에서 VU를 100배 올려도 RPS가
165에서 움직이지 않은 게 이 상태다.

### 이질성 (heterogeneity)
요청마다 비용이 다르다는 성질.
**이게 없으면 p99이라는 개념이 무의미해진다** —
모두가 똑같이 비싸면 모두가 똑같이 기다릴 뿐이다.

## 운영

### 스크레이프 (scrape)
Prometheus가 대상 서버의 `/metrics`를 주기적으로 긁어가는 것.
서버가 보내는(push) 게 아니라 Prometheus가 가지러 온다(pull).

### PromQL
Prometheus 질의어. 쿼리 모음은 [02번 문서](02-metrics-design.md)에.

### 알럿 `for` 절
조건이 참인 상태로 이 시간만큼 지속돼야 발화한다.
순간적으로 참이 되는 건 흔하므로, 노이즈를 거르는 장치다.

### 트리아지 (triage)
원래 **응급실 용어**. 환자가 몰리면 의사가 먼저 훑으면서
"이 사람 먼저, 저 사람은 대기"로 분류하는 것.

서버 운영에서도 같다. 알럿이 여러 개 울렸을 때:
- 진짜 장애는 뭐고 오탐은 뭔지
- 얼마나 심각한지
- 원인이 뭘 것 같은지

이 **첫 판단**이 트리아지다. 고치는 게 아니라 **분류하고 원인을 좁히는** 단계.
3단계에서 AI가 맡을 역할이 정확히 이것이다.

### SLI / SLO / 에러 버짓
- **SLI** — 측정 지표 (예: p99 지연)
- **SLO** — 목표치 (예: "p99 < 300ms를 99.9% 시간 동안")
- **에러 버짓** — SLO가 허용하는 실패분. 다 쓰면 배포를 멈춘다

이 프로젝트는 아직 SLO를 정의하지 않았다. 먼저 **정상 상태의
베이스라인을 알아야** 목표를 정할 수 있기 때문이다.
